# Prompt para Claude Code — Sistema de Gestão RM Modas

---

## CONTEXTO

Crie um sistema de gestão completo para a loja de moda feminina **RM Modas**, localizada em Itabaiana/SE. O sistema será acessado via navegador (desktop e mobile — iOS e Android), hospedado com frontend no **Vercel** e backend no **Railway**, com imagens gerenciadas pelo **Cloudinary**.

Não há autenticação de usuários no momento. O sistema é uso interno da loja.

---

## STACK OBRIGATÓRIA

**Frontend:** React (Vite) — deploy no Vercel  
**Backend:** Node.js com Express — deploy no Railway  
**Banco de dados:** PostgreSQL (fornecido pelo Railway)  
**Upload de imagens:** Cloudinary (variáveis de ambiente no .env)  
**ORM:** Prisma  
**Estilização:** Tailwind CSS + CSS customizado quando necessário

## MÓDULOS DO SISTEMA

---

### MÓDULO 1 — CAIXA (tela principal)

**Métricas do topo (3 cards):**
- Faturamento total do dia (ouro)
- Peças vendidas + ticket médio
- Quantidade de produtos com estoque baixo (vermelho se > 0)

**Painel esquerdo — Últimas Vendas:**
- Lista das últimas vendas do dia com: hora, nome do produto, tamanho, cor, forma de pagamento (tag colorida), valor
- Tags de pagamento: PIX (verde), Dinheiro (ouro), Débito (roxo), Crédito (azul)
- Botão "Ver histórico completo" abre modal com todas as vendas do dia com opção de cancelar cada uma

**Painel esquerdo — Estoque com Alerta:**
- Lista produtos com quantidade ≤ 3
- Ponto vermelho + nome do produto + quantidade restante
- Botão "Ir para estoque"

**Painel direito — Registrar Venda:**
- Campo de busca de produto (autocomplete por nome)
- Seleção de tamanho (PP, P, M, G, GG, Único)
- Campo de quantidade
- Campo de valor total (preenchido automaticamente ao selecionar produto, editável)
- Seleção de forma de pagamento: Dinheiro, PIX, Débito, Crédito (botões toggle, pode selecionar múltiplos para venda mista)
- Se Dinheiro selecionado: campo "Valor Recebido" aparece e calcula troco automaticamente em tempo real
- Se Crédito selecionado: campo de parcelas (1x a 12x) aparece
- Box de troco: fundo verde suave, valor em Cormorant Garamond
- Botão "Confirmar Venda" (preto com texto ouro)
- Botão "Cancelar" (borda fina, texto vermelho ao hover)

**Ao confirmar venda:**
- Débita automaticamente do estoque
- Adiciona ao histórico do dia
- Atualiza métricas em tempo real
- Limpa o formulário

**Barra inferior fixa:**
- Total do dia em ouro
- Subtotais por forma de pagamento (PIX, Dinheiro, Cartão)
- Botão "Fechar Caixa" — gera resumo do dia, salva no banco com data/hora, exibe modal de confirmação com totais

---

### MÓDULO 2 — ESTOQUE

**Listagem de produtos:**
- Grid de cards com foto do produto (quadrada, aspect-ratio 1:1)
- Cada card: foto, nome, categoria, cor, tamanho, quantidade, preço de venda
- Quantidade em destaque: verde se > 3, amarelo se ≤ 3, vermelho se ≤ 1
- Filtros no topo: categoria (dropdown), tamanho (botões toggle), cor (input texto), ordenação
- Busca por nome em tempo real

**Cadastro de produto (modal ou página separada):**
- Nome do produto
- Categoria: Vestido, Blusa, Calça, Saia, Conjunto, Acessório, Outro
- Tamanho: PP, P, M, G, GG, Único
- Cor
- Quantidade inicial
- Preço de custo
- Preço de venda
- Foto do produto (upload via Cloudinary — validação de MIME type, tamanho máximo 5MB, renomeação server-side com UUID, nunca servido como executável)
- Margem de lucro calculada automaticamente: ((venda - custo) / custo) × 100

**Entrada de estoque (reposição):**
- Botão "Repor Estoque" em cada card
- Modal: quantidade a adicionar + data (preenchida automaticamente)
- Registra histórico de entradas no banco

**Lista de reposição:**
- Botão "Lista de Reposição" no topo
- Exibe todos os produtos com quantidade ≤ 3
- Permite copiar a lista ou exportar em PDF simples (jsPDF)

- Inclui logo da RM Modas, período, totais por forma de pagamento, lista de produtos vendidos

## SEGURANÇA — OBRIGATÓRIO E NÃO NEGOCIÁVEL

Implementar **todos** os itens abaixo sem exceção. Qualquer endpoint, rota ou funcionalidade criada deve seguir estas regras integralmente.

### Parte 1 — Infraestrutura e transporte

- **Autenticação interna de API:** mesmo sem login de usuário, todas as rotas do backend devem exigir uma chave de API interna (`X-API-Key` no header), gerada como secret longo e armazenada em `.env`. O frontend envia essa chave em todas as requisições via variável de ambiente do Vercel.
- **JWT de curta expiração:** implementar JWT com expiração de 15 minutos + refresh token de 7 dias. Refresh token armazenado em cookie `httpOnly` + `Secure` + `SameSite=Strict`. Logout invalida o refresh token no banco.
- **Bloqueio de tentativas excessivas:** rate limiting por IP em todas as rotas de autenticação (máximo 5 tentativas em 10 minutos, bloqueio de 30 minutos após exceder). Usar `express-rate-limit`.
- **CORS restrito:** permitir apenas os domínios de produção do Vercel e localhost em desenvolvimento. Nunca usar `origin: *`.
- **Secrets em .env:** todas as chaves, tokens, credenciais (Cloudinary, banco, JWT secret, API key interna) devem estar em `.env`. O arquivo `.env` deve estar no `.gitignore`. Criar `.env.example` com as variáveis sem valores.
- **Rate limiting geral:** aplicar `express-rate-limit` em todas as rotas (não apenas autenticação) com limites razoáveis por IP.
- **Queries parametrizadas:** zero concatenação de strings em queries SQL. Usar Prisma em todas as operações de banco — nunca construir SQL manualmente.
- **Stack trace:** nunca expor stack traces ao frontend. Em produção, retornar apenas `{ error: "Erro interno" }` com status 500. Logar o erro completo apenas no servidor.
- **Limite de body:** usar `express.json({ limit: '10kb' })` e `express.urlencoded({ limit: '10kb' })` em todas as rotas. Rotas de upload têm limite separado de 6MB.
- **HTTPS forçado:** em produção, redirecionar qualquer requisição HTTP para HTTPS via middleware.
- **Headers de segurança:** usar `helmet` para aplicar automaticamente: `Content-Security-Policy`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Strict-Transport-Security`, `Referrer-Policy`.

### Parte 2 — Dados, uploads e integrações

- **Sanitização e validação de input:** usar `express-validator` em todas as rotas. Validar tipo, tamanho, formato e conteúdo de cada campo. Sanitizar strings contra XSS antes de salvar no banco.
- **Logs sanitizados:** nunca logar senhas, tokens, chaves de API, dados de cartão ou informações pessoais sensíveis. Usar um logger estruturado (winston ou pino) com níveis de log separados por ambiente.
- **Upload de imagens — validação rigorosa:**
  - Verificar MIME type real do arquivo no servidor (não confiar no Content-Type do cliente) usando `file-type`
  - Aceitar apenas: `image/jpeg`, `image/png`, `image/webp`
  - Tamanho máximo: 5MB
  - Renomear o arquivo com UUID antes de enviar ao Cloudinary — nunca usar o nome original do arquivo
  - Nunca servir o arquivo como executável
  - Nunca salvar arquivos de upload no servidor — enviar direto ao Cloudinary via stream
- **SSL no banco:** garantir que a conexão com o PostgreSQL do Railway use SSL (`sslmode=require` na string de conexão).
- **Retry com backoff em APIs externas:** chamadas ao Cloudinary devem ter retry automático com backoff exponencial (máximo 3 tentativas) em caso de falha de rede.
- **Proteção contra NoSQL/SQL injection:** além do Prisma, sanitizar inputs antes de qualquer uso em filtros ou buscas.
- **Proteção CSRF:** usar token CSRF em operações de mutação (POST, PUT, DELETE) via `csurf` ou implementação equivalente.
- **Variáveis de ambiente no frontend:** nunca expor a API key interna ou qualquer secret diretamente no código React. Usar variáveis `VITE_` apenas para valores que podem ser públicos (como a URL base da API). Secrets reais ficam apenas no backend.
